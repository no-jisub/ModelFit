# ModelFit 프로젝트 분석 및 개발·디자인 제안

분석일: 2026-10-04, Asia/Seoul. 현재 로컬 소스와 새로 빌드한 화면 기준이다.
이번 작업은 분석이며 서비스 코드·카탈로그·운영 설정·배포는 변경하지 않았다.

## 판단

현재 Astro 정적 사이트 구조는 유지하는 편이 좋다. 검색, 데이터 검증, 모바일 대응, 출처 표시와 테스트가 이미 갖춰져 있다. 당장의 병목은 프레임워크보다 검색 의도 판별, 호환 상태의 전달, 근거 데이터의 완성도와 배포 재현성이다.

우선순위는 **검색 정확성 → 호환 판단의 명확성 → 홈·상세 화면 개선 → 운영 측정과 데이터 검토 → 규모 확장**이다.

## 먼저 수정할 문제

### 1. 검색 결과 30개 제한으로 나머지 결과에 접근할 수 없다

- `src/components/react/SearchResults.tsx:213`에서 consumableLimit=30을 전달한다.
- `src/utils/searchCatalog.ts`는 순위를 매긴 뒤 배열을 잘라 반환한다. UI는 잘린 배열 길이를 전체 검색 결과 수로 사용한다.
- 재현: `필터` 검색은 제한 없이 72개지만 UI에 전달되는 결과는 30개다. 모델에는 더 보기 기능이 있지만 소모품에는 전체 결과를 이어 볼 경로가 없다.
- 수정: 반환값을 totalCount와 items로 구분하고 소모품에도 페이지 이동 또는 더 보기를 제공한다. 관련 결과 접기와 페이지네이션도 함께 설계한다.
- 완료 기준: 전체 72개라는 수와 현재 표시 개수를 구분하고, 모든 결과에 도달하며 필터 변경 시 페이지가 초기화된다.

### 2. 브랜드 검색이 소모품 탭을 먼저 연다

- `src/components/react/SearchResults.tsx:224`는 모델과 소모품의 최고 점수를 직접 비교해 기본 탭을 고른다.
- 서로 다른 점수 체계를 쓰므로 `로보락` 검색에서 모델 최고 50점보다 소모품 최고 85점이 높아 소모품 탭이 먼저 열린다. 로컬 브라우저에서 재현했다.
- 수정: 검색 의도를 먼저 분류한다. 브랜드명·모델번호는 모델 우선, 부품번호·소모품 종류는 소모품 우선으로 한다. 사용자가 탭을 지정했다면 그 선택을 유지한다.
- 완료 기준: `로보락`, `로보락 S8`, `AS355NSNA`, `ADQ30041405`, `필터`, `먼지봉투`의 기본 탭과 상위 결과를 사용자 시나리오로 검증한다.
- 후속: searchData의 productOptions.slice(0, 1), searchCatalog의 productOptions[0] 때문에 두 번째 이후 판매 옵션에만 존재하는 검색 표현이 빠질 수 있다. 검색 필드 합집합을 만들되 판매 상세 전체를 브라우저에 전달할 필요는 없다.

### 3. 호환 관계 개수와 확인된 개수가 혼동된다

- 모델 상세 `src/pages/model/[brand]/[model].astro:159`는 상태와 무관하게 parts.length를 `N개 확인`으로 표시한다.
- 검색 모델 카드도 `호환 소모품 N개`라는 전체 연결 수를 먼저 보여준다. 개별 관계 상태를 구분하는 기존 로직은 잘 구현되어 있지만 요약 문구가 이를 충분히 전달하지 못한다.
- 수정: `등록 부품 N개 · 공식 호환 확인 X개 · 확인 필요 Y개`처럼 관계 기준 집계를 사용한다.
- 상세 카드에서 모델 정보 확인, 모델↔부품 호환 확인, 판매자 상품 표기를 분리한다. 미확인 상태와 구매 전 주의사항은 접지 않는다.
- 완료 기준: 공식/미확인 혼합 모델과 전부 미확인인 모델에서도 요약이 정확하다.

### 4. 모델번호 안내 링크가 다른 영역을 가리킨다

- 상세 상단의 `모델번호 확인 방법`과 `확인 위치 보기`가 #model-number-guide로 연결된다.
- 해당 ID는 실제로 `제조사 공식 출처` details에 있고, `모델번호 확인 위치` details에는 없다.
- 수정: 안내 영역으로 ID를 옮기고 링크로 이동하면 해당 안내가 펼쳐지도록 한다. 헤더와 겹치지 않는 스크롤 여백, 키보드 동작도 확인한다.

### 5. 자동 배포를 다시 재현 가능하게 만들어야 한다

- 현재 npm audit는 high 6건이며 배포 워크플로의 `npm audit --audit-level=high` 조건을 만족하지 못한다.
- 이번 결과는 astro-eslint-parser, braces, eslint-plugin-astro, fast-glob, http-cache-semantics, micromatch를 포함한다. 상위 의존성까지 합친 숫자이며 서로 독립된 취약점 6종이라는 뜻은 아니다.
- 10월 3일 문서의 `수정 버전 없음 / high 7건`과 달리 이번 감사는 모든 항목에 fixAvailable=true를 반환했다. 실제 버전 변경·호환성은 아직 검증하지 않았다.
- 수정: 수정 가능한 의존성 트리를 확인하고 잠금 파일 갱신 후 기존 검사와 빌드를 재실행한다. 강제 버전 변경이나 감사 단계 제거부터 하지 않는다.
- `docs/PURCHASE_REVIEW.md`에는 최근 배포에 원격 Repository Secrets 갱신과 push가 포함되지 않았다고 기록되어 있다. 현재 원격 상태는 미확인이다. 다음 배포 전에 로컬 CSV와 CI 복원본이 같은지 비교해야 한다.
- 완료 기준: 동일 소스와 동일 카탈로그로 CI에서 빌드·검사·배포할 수 있고, 운영 결과물과 대응하는 버전이 기록된다.

## 디자인 제안

### 유지할 것

파란색 포인트, 흰색 카드, 짙은 제목, 실제 제품 이미지, 부품번호 복사, 관계별 확인 배지와 접을 수 있는 상세 정보는 유지한다. 사이트의 방향은 구매 전에 정확한 부품을 확인하는 도구다. 현재 구매 흐름에 불필요한 선택 단계나 확인 모달을 추가하지 않는다.

### 홈: 검색 행동을 중앙으로 옮긴다

현재 큰 제목과 제품·브랜드 탭이 중앙에 있고 검색창은 헤더에 있다. 데스크톱에서는 비교적 작은 검색창보다 카테고리 영역과 선명한 광고가 강하게 보인다. 홈은 카테고리 선택 후 바로 광고와 푸터로 이어져 서비스가 제공하는 근거 정보가 잘 드러나지 않는다.

제안 순서:

1. `내 가전에 맞는 소모품, 모델번호로 확인하세요`라는 제목.
2. `부품번호와 모델별 호환 근거를 함께 확인합니다`라는 짧은 설명.
3. 중앙 검색창과 `소모품 찾기` 버튼. 모델번호·부품번호 예시 제공.
4. `모델번호를 모르겠어요` 가이드 링크.
5. 제품으로 찾기·브랜드로 찾기는 보조 탐색으로 유지.
6. 실제 등록 범위와 검증 기준을 짧게 안내한 후 하단 광고.

홈에서는 헤더 검색과 큰 검색창을 중복 강조하지 않는다. 내부 페이지에는 헤더 검색을 유지한다. 검색 예시는 실제 인기 집계가 없으면 `검색 예시`라고 표기한다.

추천 규격은 검색 영역 최대 폭 720px, 입력 높이 모바일 56px, 본문 16px, 보조 문구 14px다. 강한 그림자보다 테두리와 여백으로 구분하고 모델번호가 긴 모바일 화면에서는 줄바꿈·복사 동작을 우선한다. 제휴 고지는 유지한다.

### 검색: 사진보다 정확한 모델번호와 결과 구분을 빠르게 읽게 한다

- `모델 N개 / 소모품 N개`처럼 탭 자체에 수를 표시한다.
- 정확히 일치한 모델번호를 먼저 보여주고 부분 일치·관련 모델은 별도 구역으로 둔다.
- 검색 결과는 작은 제품 이미지 + 모델명·모델번호 + 확인 상태의 목록형을 우선 검토한다. 이미지 중심 격자는 카테고리 탐색에서 유지해도 좋다.
- 검색 페이지의 헤더·본문 검색창 두 개는 활성 검색값을 공유하거나 본문 중심으로 정리한다.
- 결과 없음 화면에 검색어가 채워진 모델 등록 요청을 연결한다. 현재 재검색과 가이드 연결은 유지한다.
- 필터가 적용됐을 때 선택 상태와 전체 해제를 명확하게 표시한다.

### 모델 상세: 호환 판단에 필요한 최소 정보를 구매 버튼 앞에 둔다

현재 상세는 단순해졌지만 호환 근거와 관리 정보가 `상세 정보` 안에 들어가 구매 버튼을 먼저 보게 된다. 접기를 유지하면서 판단에 필요한 최소 정보만 위로 올리는 방식이 좋다.

카드의 권장 읽기 순서:

1. 부품명 / 정확한 부품번호 / 복사.
2. **이 모델과 공식 호환 확인** 또는 **호환 확인 필요**.
3. 관계별 공식 근거 링크와 실제 확인일 한 줄. 미확인 관계의 과거 날짜를 확정일처럼 표시하지 않는다.
4. 한 번 교체할 때 필요한 수량 / 판매 구성. `필요 2개`와 `1개입 판매`를 명확하게 분리한다.
5. 정품·호환상품의 판매자 표기와 구매 링크, 제휴 고지.
6. 관리 방법·추가 구성·전체 출처 등 상세 정보 접기.

데스크톱에서는 부품 정보 왼쪽, 판매 구성·구매 행동 오른쪽으로 배치해 긴 카드를 줄일 수 있다. 모바일은 위 순서로 쌓는다. 구매 버튼과 근거 링크의 위계를 다르게 하되, 미확인 상태를 구매 버튼 바로 위에서도 읽을 수 있어야 한다.

공식몰과 외부 판매처의 버튼 스타일은 일관된 규칙으로 정한다. 현재 쿠팡에만 primary를 주는 선택은 수익화 정책과 연결된 결정이므로, 변경 효과를 클릭과 검색 성공 지표로 비교한다.

## 개발 방향

### 가까운 개발 범위

- 검색 의도·전체 개수·페이지네이션의 반환 계약부터 정리한다.
- UI가 사용하는 관계별 확인 판정을 공통 함수와 표시용 데이터로 통일한다.
- 유지보수에서 가장 먼저 분리할 파일은 4,914줄인 global.css다. 토큰·기본 요소·레이아웃·컴포넌트 스타일로 나누되 기존 선택자 우선순위를 보존하며 화면 단위로 옮긴다. 뒤에 새 CSS를 계속 추가하는 방식은 피한다.
- 18개 관계형 CSV를 원본으로 하는 현재 흐름에 맞춰 README의 수동 TypeScript 수정 절차를 고친다. DESIGN.md의 검색 URL 생성·구매 버튼 정책도 실제 직접 상품 링크 정책과 맞춘다.
- 데이터 검토는 구매 링크가 있는 미확인 관계와 여러 모델이 공유하는 부품부터 한다. 132개를 추정으로 official로 바꾸지 않는다.

### 확장 전 필요한 작업

- createCatalogRepository는 존재하지만 현재 페이지와 검색은 정적 models/consumables를 직접 사용한다. 저장소 환경변수만 바꿔 사이트 전체가 SQL로 전환되는 상태가 아니다.
- 현재 규모에서는 정적 생성을 유지한다. 모델 수를 늘리기 전 검색 페이지 HTML·인덱스·빌드 시간 예산을 정하고 실제 병목을 측정한다.
- 이번 비압축 결과는 `/find/index.html` 257,590 bytes, `/search-index.json` 136,287 bytes다. 검색 데이터가 JS 밖에 있다는 것만으로 전체 전송량이 작은 것은 아니다. 검색 성능 검사에 HTML·JSON과 실제 입력 반응도 포함한다.
- 이후 빌드 데이터 공급부터 저장소 인터페이스에 연결하고, 대규모 검색에 한해서 서버 검색과 페이지네이션을 검토한다. 프레임워크 전면 교체는 현재 분석에서 필요성을 찾지 못했다.

### 운영과 제품 기능

- 기존 검색·구매 이벤트를 이용해 검색 결과 없음 비율, 정확한 모델 도달률, 공식 근거 열람률, 모델별 구매 링크 클릭률을 본다. 외부 구매 링크 클릭은 실제 주문 완료와 다르다.
- 10월 3일 기록상 운영 GA ID가 없었다. 실제 수집 상태는 별도 확인이 필요하다. 구매 이벤트에는 모델 식별자를 추가하면 모델별 진단이 쉬워진다.
- 작은 다음 기능은 최근 본 모델·내 제품 저장을 로컬 저장소로 제공하는 것이다. 로그인 없이 재방문 가치를 시험할 수 있다.
- 사진 OCR, 계정 기반 교체 알림, 가격 비교, 대규모 모델 추가는 호환 데이터 품질과 실제 사용 수요를 확인한 뒤 검토한다. OCR을 추가하더라도 인식된 모델번호를 사용자가 확인하는 단계가 필요하다.
- 제보 접수·관리자 권한·App Check 강제 적용은 운영 계정으로 실제 흐름을 별도 확인한다.
